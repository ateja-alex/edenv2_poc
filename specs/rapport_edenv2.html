Rapport d'analyse fonctionnelle et technique

Eden / std-eden — cartographie en vue d'une refonte

Référencement du périmètre fonctionnel et technique de l'ERP : ce qu'il y a dedans, comment c'est construit, et ce qui s'écarte des standards. Ce document est un inventaire, pas une spécification de rétro-ingénierie.

Dépôt std-eden (branche feat/docker_alex) Framework Eden — submodules app/Eden + public/eden Version Eden tag Version_2026080120 Date 17/09/2026 Méthode lecture statique du code, aucun run, aucune modification

Synthèse

std-eden est une coquille Laravel de 793 lignes qui héberge un framework applicatif maison de 387 000 lignes. Eden n'est pas une bibliothèque au-dessus de Laravel : il en remplace le routage, le modèle de données, la couche d'écrans, l'authentification et les migrations. Laravel fournit le conteneur, Blade, Eloquent et quelques façades ; tout le reste est propriétaire.

Ce que couvre le produit

Un ERP complet : gestion commerciale achat et vente, articles et stock multi-entrepôts, CRM, projets et tâches, saisie des temps, RH, comptabilité et trésorerie, recouvrement, règlements, facturation électronique, e-commerce, blog, extranet, planning, tickets, GED, messagerie, reporting, import/export — 23 domaines fonctionnels, 182 objets métier, 772 routes, 15 intégrations tierces.

Ce qui le rend paramétrable

Deux leviers superposés : 400 fonctionnalités activables par fichier de configuration (dont 353 exposées dans une IHM d'administration), et un moteur no-code — tables, champs, listes, formulaires, rapports et vues SQL « libres ». Un champ porte 63 propriétés paramétrables, dont l'affichage, l'obligation et la lecture seule conditionnels, et le calcul par requête. C'est ce socle, détaillé en §2.4, qui représente le périmètre le plus coûteux à reproduire.

Les cinq constats qui structurent une refonte

  1. La configuration est du code. Le paramétrage écrit des fichiers PHP dans storage/app/ qui sont ensuite includeés : fonctionnalités, mise en page des fiches, formulaires libres, menus, filtres JS. Il n'existe pas de frontière nette entre « réglage client » et « code source », ni de schéma qui décrive ce qui est réglable.
  2. Le système de fonctionnalités marche, mais il a dérivé. 87 % des clés sont réellement branchées (823 appels dans le code). Restent 51 clés mortes issues d'un regroupement jamais nettoyé, 37 réglages affichés sans effet détecté, 49 réglages invisibles dans l'IHM, et 2 fautes de frappe dont une casse silencieusement l'intégration SharePoint.
  3. Quatre mécanismes ne se portent pas tels quels. Les migrations maison (1 219 fichiers sans rollback ni historique), l'évaluation de conditions et de modèles de documents par eval() / Blade dynamique, le DDL construit par concaténation, et une authentification qui n'utilise pas du tout Laravel (zéro occurrence de Auth::).
  4. La logique est concentrée dans très peu de fichiers. Dix fichiers PHP dépassent 60 Ko ; Document_management.php (347 Ko) et Element_management.php (180 Ko) portent à eux seuls l'essentiel du métier documentaire. Les vues et les managements représentent 63 % du code.
  5. Il n'y a ni filet ni documentation. Aucun test automatisé exploitable (phpunit.xml au format PHPUnit ≤ 9 avec PHPUnit 11 déclaré), aucune CI, et le dossier docs/tech/ référencé par le CLAUDE.md du projet n'existe pas sur cette branche. Le front repose sur Vue 2.7, en fin de vie depuis fin 2023.

Lecture d'ensemble. Eden est un produit mûr et large, façonné par 13 344 commits et une cadence de version mensuelle. Ses choix non standard ne sont pas des accidents : ils servent un objectif assumé — personnaliser chaque instance client sans redéployer de code. Le coût s'est reporté sur la traçabilité, la sécurité et la testabilité. Une refonte a donc deux questions distinctes à trancher : quel périmètre fonctionnel reprendre (sections 1 et 2) et quel modèle de personnalisation adopter à la place (sections 3 et 5).

1.1 Mécanique — validée

Le mécanisme fonctionne, il est cohérent de bout en bout, et il est entièrement basé sur des fichiers PHP — aucune table de configuration en base.

① DÉFAUTS         app/Eden/Config/fonctionnalites.php          400 clés, valeurs standard
                                    ▲
② SURCHARGE       storage/app/eden_fonctionnalites.php        25 Ko, propre à l'instance
   CLIENT         + storage/app/eden_fonctionnalites_specifiques.php   (clés sur mesure)
                  + storage/app/eden_fonctionnalites_pdf_par_defaut.php
                                    │
③ FUSION          fonctionnalites.php fusionne $standard ← $specifique
                  · array_merge sur un seul niveau pour les valeurs tableau
                  · régénère les clés plates historiques depuis gescom_document
                  · base64_decode des clés de type « password »
                                    │
④ EXPOSITION      config('fonctionnalites')
   LARAVEL        mergeConfigFrom(Config/*.php) dans EdenServiceProvider::register()
                                    │
⑤ LECTURE         fonctionnalite('ma_cle')          Helpers/fonctionnalite.php
                  └ si moi()->profil_id et fonctionnalites_par_profil[cle][profil]
                      → valeur spécifique au profil
                  └ sinon valeur globale, sinon null
                  ⚠ une partie du code lit directement config('fonctionnalites.xxx')
                                    │
⑥ ÉCRITURE        POST parametrage/fonctionnalites/enregistrer
                  Parametrage_controller::fonctionnalites_enregistrer()
                  · sauvegarde horodatée dans storage/app/sauvegardes_fonctionnalites/
                  · var_export() du POST complet → réécriture du fichier PHP
                  · opcache_invalidate()

Points validés

  • Surcharge par profil utilisateur : la clé réservée fonctionnalites_par_profil[clé][profil_id] permet un réglage différencié par profil. Implémenté et lu par le helper.
  • Versionnement des sauvegardes : chaque enregistrement archive l'état précédent (2 sauvegardes présentes dans cet environnement).
  • Invalidation OPcache explicite après écriture — nécessaire puisque la configuration est du PHP exécutable.
  • Auto-diagnostic : Fonctionnalite_management::recuperer_difference_vue_config() compare déjà les clés de l'IHM à celles de la config et affiche les manquantes. Le framework connaît son propre problème de dérive.
  • Extensibilité de l'IHM : Fonctionnalite_management::enfants() scanne le dossier Managements/Fonctionnalites/ par réflexion — ajouter une classe crée un onglet de paramétrage.

Trois fragilités confirmées dans la mécanique.

  1. La configuration est du code PHP généré puis exécuté. Deux des trois écritures (fonctionnalites_specifiques_enregistrer(), enregistre_pdf_par_defaut(), Parametrage_controller.php l. 220-243 et 286-305) construisent le fichier par concaténation de chaînes sans échappement, là où l'écriture principale utilise correctement var_export(). Une valeur contenant un guillemet suffit à casser — ou à détourner — le fichier de configuration.
  2. Les secrets d'intégration sont encodés, pas chiffrés. Les clés de type password (identifiants de connexion aux services tiers) sont stockées en base64 dans un fichier PHP du dépôt de travail et redécodées à chaque chargement de configuration. L'encodage base64 est réversible : ce n'est pas une protection.
  3. Deux voies de lecture coexistent. Le helper fonctionnalite() applique la surcharge par profil ; les appels directs à config('fonctionnalites.xxx') ne l'appliquent pas. Le comportement diffère donc selon le point d'appel.

1.4 Legacy et doublons

  • Config/fonctionnalites_integrations.php est un doublon mort : son contenu entier est return include(…/fonctionnalites.php), avec un commentaire daté de 2022 demandant de ne plus l'utiliser. Le array_merge(config('fonctionnalites'), config('fonctionnalites_integrations')) du helper fusionne donc un tableau avec lui-même — sans effet, mais exécuté à chaque requête.
  • Migration « v2 » inachevée : 5 modules portent le suffixe _v2_management, 4 ne l'ont pas. La vue parametrage_fonctionnalites_affichage_liste_fonctionnalites.blade.php et sa variante _v2 cohabitent dans le même dossier.
  • Sauvegarde asymétrique : le module principal archive l'état précédent avant écrasement ; les modules « spécifiques » et « PDF par défaut » n'archivent rien.
  • Enregistrement par instantané complet : chaque sauvegarde réécrit l'intégralité de l'état posté depuis le composant Vue, pas un delta. Une clé ajoutée en code mais non reprise côté front peut être effacée au prochain enregistrement.

Verdict. Le système de fonctionnalités paramétrables est réel, opérationnel et massivement utilisé — 823 appels dans le code, 87 % des clés effectivement branchées. Sa dérive est celle d'un mécanisme vivant depuis longtemps : ~13 % de clés mortes, 37 réglages sans effet, 49 non exposés, 2 fautes de frappe dont une casse une intégration. Pour une refonte, le modèle est à conserver ; son support (fichiers PHP générés, secrets en base64, absence de schéma et de validation) est à remplacer.

Zoom : l'affichage conditionnel

Eden ne se contente pas de montrer ou cacher un champ. Il sait le rendre conditionnellement obligatoire, conditionnellement en lecture seule, et cela à deux niveaux distincts :

  • Au niveau du champ — la condition s'applique partout où le champ apparaît, dans tous les formulaires.
  • Au niveau du placement du champ dans un formulaire donné — le même champ peut donc se comporter différemment selon l'écran.

Les conditions s'écrivent dans une syntaxe proche de JavaScript, mêlant les valeurs de l'enregistrement en cours de saisie et des méthodes du composant :

// masquer tant que la case n'est pas cochée
condition_affichage_v_if  : "document.a_livrer_chez_client"

// rendre obligatoire seulement si aucune adresse n'est renseignée
condition_obligatoire     : "document.adresse_de_facturation_texte == ''
                             || document.adresse_de_facturation_id == 0"

// s'appuyer sur une méthode du formulaire
condition_affichage_v_if  : "$root.utilisation_devise_etrangere()"

Deux variantes sont proposées : v-if retire le champ du document, v-show le masque seulement. Les expressions sont évaluées côté navigateur dans le formulaire ; hors formulaire — conditions d'envoi d'une pièce jointe d'email, enregistrement conditionnel d'un modèle de document — la même syntaxe est réécrite puis exécutée côté serveur par eval_condition_js(), ce qui en fait un point de vigilance sécurité (voir §5.3).

Les types de champs structurels (onglet, titre, HTML, sous-formulaire) n'existent jamais dans les fichiers de migration livrés : ils ne sont créés que depuis l'IHM de paramétrage. C'est un bon indicateur de ce qui relève réellement du no-code.

Bandeau de calculsTotaux et indicateurs au-dessus ou au-dessous de la liste, recalculés avec les filtres courants : COUNT, SUM, AVG, moyenne sur comptage, avec unité, icône, condition d'affichage et état déployé par défaut. Chaque calcul peut être ventilé par une autre colonne et limité aux N premières valeurs.
Sous-totaux à la demandeL'utilisateur choisit jusqu'à trois niveaux de regroupement ; les lignes de sous-total sont injectées et le tri est forcé en conséquence.
FiltresWidget déduit automatiquement du type de champ (texte, liste, montant, date, recherche d'élément, utilisateur, famille). Trois emplacements : filtres standards, menu de gauche, filtre de statut. Un filtre peut porter sur un champ lié via une jointure.
Persistance et filtres nommésPage, filtres et tri sont mémorisés par utilisateur et par liste. Un jeu de filtres se sauvegarde sous un nom et se rappelle ensuite.
Coloration conditionnelleDes règles de couleur de ligne s'appuient sur des recherches avancées ; la première règle qui correspond l'emporte. Une couleur de fond fixe peut aussi être posée sur une colonne entière.
Mise en forme des colonnesAlignement, troncature au-delà de N caractères, interdiction du retour à la ligne, comportement responsive, lien cliquable vers l'élément ou vers un autre élément, ouverture du formulaire en modale, affichage d'avatars. Pas de largeur de colonne configurable ni de réordonnancement par glisser-déposer côté utilisateur final.
Droits par colonne, filtre et calculChacun porte sa propre liste de profils autorisés : deux utilisateurs peuvent voir la même liste avec des colonnes différentes.
Activation finePar liste, on coupe individuellement : filtres, recherche, recherche avancée, export, création (avec condition), actions groupées, actions individuelles, options, kanban, glisser-déposer, cases à cocher, options mobiles.
Vues alternativesUne même liste peut proposer plusieurs vues commutables — typiquement tableau et kanban — reliées entre elles.
PaginationNombre de lignes par défaut global, surchargeable par liste et par requête. Cas forcés : 1000 lignes pour une carte, 50 en kanban horizontal, 1000 en kanban vertical.
Sélection et actions de masseLe « tout sélectionner » récupère les identifiants correspondant aux filtres courants sans charger les lignes — conçu pour des dizaines de milliers d'enregistrements — et affiche une synthèse de la sélection. Actions disponibles : modification en masse (avec deltas relatifs sur dates et montants, ajout sans écrasement sur les multi-sélections), suppression en masse, création de tâches en masse, impression groupée de modèles de document (PDF fusionné ou archive), envoi d'email en masse, validation en masse — chacune soumise à un droit dédié.
CorbeilleAffichage avec ou sans les éléments inactivés, ou uniquement les inactivés.
Détail dépliableUne ligne peut déplier un bloc de détail sans changer d'écran.

Limite structurante à connaître. Il n'existe aucun filtre post-agrégat (pas de HAVING). On peut restreindre les lignes qui entrent dans un calcul, mais pas filtrer les résultats sur la valeur calculée — impossible d'écrire « n'afficher que les clients dont le CA dépasse X » directement dans une liste. Les sous-totaux ne servent qu'au regroupement, sans seuil applicable.

2.5 Modes de gestion métier paramétrables

Au-delà des capacités transverses, l'ERP sait prendre en charge plusieurs variantes de fonctionnement du même processus. Ce sont ces modes qui font qu'une instance ressemble peu à une autre — et qui doivent être arbitrés un par un dans une refonte. Les groupes ci-dessous reprennent le découpage réel de l'écran de paramétrage gestion commerciale (17 onglets, 159 réglages).

2.5.1 Stock

SujetCe qui existe
ValorisationPrix d'achat moyen pondéré recalculé à la volée sur les factures d'achat des 12 derniers mois ; à défaut, dernier prix d'achat mémorisé sur la fiche article. Ni FIFO, ni LIFO, ni CUMP perpétuel — pas de valorisation mouvement par mouvement.
Multi-entrepôtsStock par entrepôt, avec vues agrégées « tous entrepôts ». Entrepôt par défaut paramétrable, et option de gestion de l'entrepôt à la ligne du document.

5.3 eval() et Blade dynamique sur du contenu configuré

Helpers/eval_condition_js.php · Helpers/blade_compile.php · Providers/EdenServiceProvider.php · ~20 vues Blade

Trois évaluateurs distincts exécutent du code construit à partir de données paramétrables.

// Helpers/eval_condition_js.php — conditions d'affichage paramétrées
//   réécrit "$root.moi.xxx" → "moi()->xxx", "client.champ" → "$element->champ"
return eval('return '.$condition.';');

// Helpers/blade_compile.php — modèles de documents éditables en base
function blade_compile($value, array $args = array()) {
    return \Blade::render(html_entity_decode($value), $args);
}
  • eval_condition_js() évalue en PHP une condition saisie dans l'écran de paramétrage.
  • blade_compile() compile et exécute du Blade — donc du PHP — provenant de champs de base de données (modèles de documents, blocs de contenu, publipostage).
  • Les directives @champ et @traduction utilisent eval() sur leurs arguments au moment de la compilation Blade (arguments écrits par les développeurs : risque moindre, pattern non standard tout de même).
  • Côté navigateur, une vingtaine de vues appellent eval(condition) / window.eval(...) pour les mêmes conditions d'affichage.
  • Un second eval() PHP existe dans Elements/Parametrage_balise_publipostage_management.php.

Le périmètre de confiance est donc « tout administrateur fonctionnel capable d'éditer un modèle de document ou une condition d'affichage peut exécuter du PHP arbitraire sur le serveur ».

5.8 Cache applicatif en session

Managements/Cache_management.php (37 Ko) stocke le cache des métadonnées — classes de management résolues, éléments, traductions, droits — dans la session PHP de l'utilisateur (session()->put('cache.…'), session()->forget('cache')), et non dans le cache Laravel. Conséquences : cache non partagé entre utilisateurs, rechargé à chaque nouvelle session, taille de session importante, et invalidation qui dépend du cycle de vie de la session.
